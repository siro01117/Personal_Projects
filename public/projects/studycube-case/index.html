스터디큐브 — 독서실 운영 플랫폼

실제 운영 중인 독서실에 직접 만들어 배포한 시스템이다. 관리자 한 명이 이 화면 하나로 출결·순찰·벌점·도시락을 처리한다.

화면과 데이터는 개인정보 보호를 위해 전부 더미로 다시 만들었지만, 구조와 동작 규칙은 실제와 같다. AI에게 일을 시키고 결과를 검증하는 방식으로 기획부터 배포까지 직접 진행했다.

Design Decisions

왜 이렇게 만들었나

기능이 아니라 결정의 기록이다. 카드마다 실제로 부딪힌 제약과 그걸 어떻게 정리했는지를 적었다.

01

출결 기록은 고치지 않고 쌓기만 한다

입실·퇴실을 기록할 때마다 attendance_event라는 표에 새 줄을 더할 뿐, 이미 쌓인 줄은 절대 고치지 않는다.
상태값 하나를 켰다 껐다 하는 방식이면 "언제 그랬는지"가 사라지고, 나중에 뭔가 잘못됐을 때 무엇을 고쳤는지도 안 남는다. 그래서 지우는 것도 막고, 방금 찍은 마지막 기록 하나만 취소하게 했다.
02

벌점 점수는 준 순간 그대로 저장한다

벌점을 줄 때 그 순간의 점수를 기록 자체에 박아 넣는다. 기준표를 나중에 다시 찾아보지 않는다.
이렇게 안 하면 나중에 벌점 기준을 바꿨을 때 지난달 기록까지 같이 흔들린다. 누적 점수는 그냥 기록을 다 더한 값이고, 잘못 준 벌점은 점수를 빼는 게 아니라 그 기록 자체를 지운다.
03

순찰 기록에도 그날의 좌석 번호를 그대로 남긴다

순찰 기록마다 학생 정보뿐 아니라 그때 앉아 있던 좌석 번호도 같이 저장한다.
학생이 자리를 옮긴 뒤에 지난 순찰 기록을 다시 보면, 지금 자리가 아니라 그날 실제로 앉아 있던 자리 그대로 나와야 맞는다. 지금 좌석을 거꾸로 찾아 보여주면 이 부분이 틀어진다.
04

자주 안 바뀌는 값은 화면이 아니라 코드에 고정한다

회비, 지각 기준 시간, 벌점 항목 같은 값은 설정 화면을 따로 만들지 않고 코드 안에 숫자로 못 박았다.
지점이 하나뿐이고 규칙도 거의 안 바뀌는데, 그걸 위해 설정 화면을 만들면 들이는 품이 얻는 것보다 크다. 다만 지점이 늘어날 걸 대비해서 모든 표에 지점 구분값은 미리 넣어뒀다.
05

자주 안 쓰는 조작은 눌러야 보이게 숨겼다

학생 상태는 다니는 중 · 쉬는 중 두 가지로 줄이고, 자리 비우기·자리 옮기기 같은 조작은 우클릭(터치는 꾹 누르기) 메뉴 안으로 옮겼다.
매일 쓰는 화면에 어쩌다 한 번 쓰는 버튼까지 늘어놓으면 정작 자주 쓰는 것이 눈에 안 들어온다. 위 데모에서 좌석을 우클릭하면 이 메뉴를 그대로 볼 수 있다.
06

공개 신청폼은 이름 + 숫자 5자리로 확인한다

전화번호가 없는 학생도 있어서, 로그인 대신 이름과 5자리 번호로 본인을 확인한다. 짧은 시간에 너무 많이 틀리면 그 이름을 잠시 잠근다.
숫자 4자리는 생일(월일)과 겹쳐 보이는 경우가 있어 5자리로 늘렸다. 요청마다 서버가 새로 뜨는 구조라 실패 횟수를 메모리에 세워둘 수 없어서, 실패 횟수를 데이터베이스에 직접 기록했다 — 15분 안에 10번 틀리면 맞는 번호를 넣어도 한동안 막힌다.
Data

운영 데이터 추이

실제로 부딪힌 것들

증상 → 원인 → 고친 방법 → 배운 것. 실제로 만나서 고친 문제들이다.

01"11"을 쳤더니 "01"이 되는 입력칸
증상

시간이나 번호를 입력칸에 두 자리 치면, 앞자리가 사라지고 대신 0이 붙었다.

원인

글자를 입력할 때마다 바로 자릿수를 맞추는 처리를 걸어놔서, 다 치기도 전에 값을 고쳐버리고 있었다.

수정

입력하는 동안엔 친 그대로 두고, 입력칸에서 포커스가 빠져나갈 때만 자릿수를 맞추도록 나눴다.

배운 것

입력 중엔 손댄 값을 건드리지 않고, 다듬는 건 입력이 끝난 다음에 한다 — 이후 모든 입력칸에 이 규칙을 그대로 적용했다.

02먼저 보낸 요청이 늦게 도착해 화면을 덮어쓴 문제
증상

학생 A 기록을 보다가 빠르게 B로 넘어가면, 뒤늦게 도착한 A의 응답이 B 화면을 덮어써 버렸다.

원인

요청이 나간 순서와 응답이 돌아오는 순서가 항상 같다고 가정하고, 이걸 확인하지 않았다.

수정

요청을 보낼 때 지금 보고 있는 대상을 따로 기억해두고, 응답이 오면 그때도 여전히 같은 대상을 보고 있는지 확인한 다음에만 화면에 반영했다.

배운 것

응답은 보낸 순서대로 돌아온다고 믿으면 안 된다 — 항상 "지금도 여전히 유효한 요청인가"를 확인한다.

03좌석 하나만 바뀌어도 화면 전체가 깜빡이던 문제
증상

좌석 하나 상태만 바뀌어도 배치도 전체가 매번 처음부터 다시 그려지며 깜빡였다.

원인

좌석 하나를 그리는 코드를 화면 전체를 그리는 함수 안쪽에 넣어놨더니, 매번 새로 만든 것처럼 취급돼 전체가 다시 그려지고 있었다.

수정

좌석을 그리는 코드를 바깥으로 꺼내 한 번만 정의해두고 재사용하게 했다.

배운 것

화면 조각을 그리는 코드는 항상 바깥에 한 번만 정의해두고, 그리는 함수 안에서 새로 만들지 않는다.

04화면마다 총원 숫자가 서로 다르게 나오던 문제
증상

요약 화면, 좌석 배치도, 학생 목록에 나오는 총 인원수가 화면마다 달랐다.

원인

인원을 세는 기준이 화면마다 조금씩 달라서(예: 쉬는 중인 학생을 빼는지 마는지), 각자 다른 조건으로 세고 있었다.

수정

인원을 세는 방식을 한 곳에 딱 하나로 통일하고, 모든 화면이 그 하나를 그대로 가져다 쓰게 했다.

배운 것

같은 개념(예: 총원)은 코드 전체에서 세는 방법이 딱 하나여야 한다. 화면마다 각자 세면 언젠가 어긋난다.

05화면 전용 코드를 잘못된 곳에서 불러와 배포가 깨진 문제
증상

배포할 때만 빌드가 실패했고, 내 컴퓨터에서는 멀쩡히 잘 돌아가서 원인을 찾기 어려웠다.

원인

브라우저(화면)에서만 돌아야 하는 코드 조각을, 서버에서 미리 돌아가는 코드가 실수로 가져다 쓰고 있었다.

수정

여러 화면이 공통으로 쓰는 순수 계산 코드를 서버·화면 어느 쪽에서도 안전한 별도 파일로 분리해뒀다.

배운 것

서버에서도 화면에서도 같이 쓸 코드는 처음부터 어느 쪽 전용도 아닌 자리에 놓아둔다.

Architecture

전체 구조 한 장

들어오는 입구는 세 개, 데이터를 담는 곳은 하나다.

지점이 늘어도 데이터가 섞이지 않는 구조 — 모든 표의 각 줄마다 어느 지점 것인지 표시를 심어뒀다. 지점이 늘어도 표 구조를 다시 안 짠다.
권한은 역할이 아니라 "이 동작을 할 수 있는가"로 매번 따진다. 역할이 늘어나도 권한 체계를 다시 안 짠다.
새 화면은 조립하듯 등록만 하면 추가되게 만들었다 — 화면 하나를 늘릴 때마다 이동 경로나 권한 체계를 처음부터 다시 짜지 않는다.
